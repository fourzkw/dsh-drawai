# 绘制、任务队列与视频导出优化方案

状态：P0 已接入分阶段采集和可重复基准工具，宿主局部基线已运行；端到端与压力测试覆盖见 [P0 使用说明](performance-baseline.md)。第一批 P1 已交付计算优化和应用内图片/视频队列，视频导出也已迁移到宿主独立渲染、编码与保存，能力及限制见 [优化记录](performance-optimizations.md)。宿主绘制队列、视频顺序解码及持久化检查点尚待实现。整体迁移边界和实施顺序以 [后台迁移评估](background-workflow-assessment.md) 为准；本文第 5.1 节的浏览器帧上传优化已被宿主渲染替代，第 5.2/5.3 节的管道化和缓存复用仍是后续候选。

目标是缩短绘制与导出的等待时间，并支持连续提交多个绘制任务。保持用户选择的分辨率、帧率、碎片档位、颜色数和背景选项；不通过减少帧数或降低画质实现默认加速。实际收益用固定素材测量，不预先承诺倍数。

## 1. 当前实现与优化边界

| 环节 | 已有实现 | 需要解决的问题 |
|---|---|---|
| 视频绘制 | 常驻 Worker 池，最多 4 个线程；抽帧与计算部分重叠；只算选中的碎片档位 | 浏览器逐帧 seek、PNG 编码、Base64 传输及 PNG 再解码仍有开销；当前池内排队的是帧，不是用户任务 |
| 重复计算 | 完全相同 PNG 与参数复用 SVG，适配检查通过后复用调色板 | 近似整帧复用已移除；需要继续测精确命中率、调色板检查/拒绝及刷新成本 |
| 任务状态 | 以会话、路径、页面保存应用内状态，已有排队、顺序调整、暂停、重试和有限历史 | 宿主队列和持久化尚未实现；同页后续计算仍受前一结果应用/保存状态阻塞，批量多选提交尚待实现 |
| 视频导出 | 宿主 Worker 逐张渲染 SVG，FFmpeg 离线编码并自动保存 | 浏览器帧上传已移除；逐帧 PNG 写盘、准备与编码两阶段相加、任务历史未跨宿主重启持久化仍可改进 |
| 导出正确性 | 固定帧率、完整帧数验证、片段音频、白底、目录试写 | 优化后必须保留，禁止恢复成按播放时钟跳帧的实时录制 |

目前尚无完整的分阶段耗时数据，因此不能断言某一项在所有素材中都是主要瓶颈。

## 2. 先建立可比较的性能基线（P0）

绘制记录：源读取、解码/seek、缩放、PNG 编码、传输、等待 Worker、像素处理、量化、轮廓生成、SVG 序列化和写入耗时。

导出记录：SVG 读取、图像解码、画布渲染、PNG 编码、传输、排队、FFmpeg 编码、下载耗时。同步记录各阶段处理速度、主线程长任务、进程峰值内存和临时文件大小。

固定测试集包含：静止画面、缓慢运动、快速切镜、复杂彩色画面、透明背景、长视频，以及现有图片校准夹具。视频覆盖 480p、1080p，30fps 和 29.97fps；4K 与长片作为压力测试。

同一机器、同一参数进行冷启动与热启动测试，至少重复 3 次，报告中位数与波动范围。计时日志放入 `.drawai-cache/`，界面仅展示阶段、速度、进度及有依据的预计剩余时间。

## 3. 用户任务队列（P1，核心能力）

### 提交与操作

- 图片和视频绘制共用任务管理器，支持逐个加入及多选批量加入。
- 队列面板列出来源、所属画布、参数摘要、状态、进度、耗时和错误；按工作区组织，并按会话权限筛选。
- 默认 FIFO；尚未开始的任务可调整顺序、移除、修改参数后重新提交。
- 支持单任务暂停、恢复、取消和重试，以及“暂停队列”。暂停队列只停止启动后续任务，当前任务继续完成。
- 默认同时执行 1 个视频绘制任务，任务内部使用共享 Worker 池。首版图片任务也按统一顺序调度，不允许每个任务各建一套线程池。
- 一个任务失败不阻塞后面的任务。失败原因可复制，重试保留原参数。

### 状态与身份

任务状态包括：`queued`、`preparing`、`running`、`pausing`、`paused`、`ready_to_apply`、`succeeded`、`failed`、`cancelled`、`interrupted`。

运行结束先进入 `ready_to_apply`；成功加入原画布并完成保存确认后才进入 `succeeded`。等待加入画布的结果不占计算槽位，后续任务可以继续。

每个任务有独立 `taskId`，绑定 `workspace + sessionId + canvasPath + page + sourceNodeId + sourceClip/图片摘要`。提交时冻结绘制参数和算法版本，另存幂等请求标识，防止重复点击生成多个任务。用户明确发起“再次绘制”时允许生成新任务。

### 持久化与结果应用

- 任务管理由宿主负责；浏览器只提交、订阅状态及应用结果。任务元数据和检查点存入画布目录的 `.drawai-cache/tasks/`，使用临时文件加原子替换更新。
- 切换标签、对话或关闭进度面板不会取消任务。主动关闭画布时，有未完成任务则提供“后台继续 / 取消任务”的明确选择，避免意外丢失。
- 页面没有挂载时，结果保留在原任务中；返回原页面后通过原有修改、撤销和保存通道加入一次。禁止直接覆盖整个 `.drawio` 快照。
- 应用结果前验证源节点、媒体摘要、页面及图层状态。源被删除、替换或锁定时保留结果并提示处理，不能写入其他画布。
- 同一画布、同一页面的多个结果依次应用，收到保存确认后再应用下一个；保存冲突时保留待应用结果，不重复插入。
- 重启后恢复任务列表，将未结束的运行任务标记为 `interrupted`，由用户确认恢复队列。不能把“元数据恢复”显示成“绘制已恢复”。

### 暂停和断点恢复

暂停在当前有限在途帧处理完并按序写入后生效。检查点保存连续完成帧数、采样起点、帧率、调色板、复用状态和输入摘要；恢复从下一帧开始，不重写完成帧。

输入内容或算法版本变化时不自动续绘，提示重新提交。浏览器兼容路径在首版可只提供重新开始；断点续绘先在宿主执行路径中实现和验证。

分阶段交付时，P1 的暂停/恢复先保证当前宿主进程内正确，重启后恢复列表并明确提供“重新开始”；P2 检查点验证通过后才开放跨重启续绘。界面必须区分这两种恢复能力。

## 4. 绘制提速（P1，与队列共用执行器）

推荐的新视频路径：

```mermaid
flowchart LR
  A[排队任务] --> B[FFmpeg 顺序解码与缩放]
  B --> C[有界 RGBA 帧缓冲]
  C --> D[共享绘制 Worker 池]
  D --> E[按帧号提交 SVG 与检查点]
  E --> F[保留结果并加入原画布]
```

1. **宿主顺序解码。** 使用已有 FFmpeg 依赖解码原视频，按任务时间范围和帧率采样，直接输出目标尺寸的 RGBA，减少浏览器反复 seek、PNG 编码/解码及往返上传。管道输出必须按完整帧大小组装，不能把一次 stdout 数据块误认为一帧。
2. **复用现有算法。** Worker 增加原始像素入口，与现有 PNG 入口调用同一个绘制内核。图片队列也进入 Worker，保持其已有画风与分析行为，不直接套用视频的简化入口。
3. **减少数据复制。** 对明确拥有所有权的独立 ArrayBuffer 使用转移；不直接转移 Node Buffer 池的底层内存。进入 Worker 后避免再次完整复制像素。[Node Worker 文档](https://nodejs.org/api/worker_threads.html#considerations-when-transferring-typedarrays-and-buffers)
4. **限制内存。** 初始沿用最多 4 个计算线程，再根据基准决定是否开放自动档位。在途帧和乱序结果都设上限；容量根据实测单帧工作集计算，不能只按原始 RGBA 大小估算。队列满时暂停解码读取。
5. **收紧重复工作。** 已移除近似整帧复用。当前用上传 PNG 内容摘要与完整绘制参数键复用相邻完全重复帧，缓存命中仍写入对应帧的时间位置；不同 PNG 编码保守地重新计算。调色板经过当前工作图前景颜色适配检查，并以实际生成帧控制刷新周期；共享命中不能延后刷新。
6. **降低进度开销。** 普通进度消息合并到每秒约 4 次，预览单独限频；完成、取消、错误立即推送，不因节流延迟状态。

抽帧路径变化必须单独回归：FFmpeg 与浏览器可能存在时间采样和色彩转换差异，不能仅凭输出帧数就宣布等价。使用带帧号的源片、切镜和透明素材验证首尾采样、颜色、方向和画风；未经验证的路径保留兼容开关，不做静默切换。无 FFmpeg 时保留现有浏览器路径，并明确其需要应用保持打开。

## 5. 导出端高优先级优化（P1/P2）

### 5.1 有界预取与二进制上传（先交付）

- 初始采用 2～4 个在途帧，并按分辨率和内存上限缩减。用独立画布或明确的像素快照，防止异步 PNG 编码拿到下一帧的画面。
- 重叠 SVG 预取、图像解码、PNG 编码和上传；服务端最后按帧号提交。
- 控制请求继续使用 JSON，帧数据改用二进制请求体。保留同源、自定义头、会话/画布权限及令牌校验；二进制入口单独设请求大小限制。
- 每帧分块状态按 `(taskId, frameIndex)` 保存，校验分块偏移；不能继续用“只能接收下一提交帧”的单上传状态。
- 重试以分块摘要/幂等标识识别重复，不能重复追加字节；已确认的帧不重复编码。失败停止新增数据，清理当前任务。
- 下载改为带授权的二进制流，减少 Base64 解码及多次拼接；不暴露可任意访问的本地文件路径。

### 5.2 边准备边编码（随后交付）

```mermaid
flowchart LR
  A[有限 SVG 预取] --> B[逐帧栅格化为白底 PNG]
  B --> C[二进制上传与有限乱序缓冲]
  C --> D[按序写入 FFmpeg 管道]
  D --> E[固定帧率 MP4 或 WebM]
```

首批帧准备好就启动 FFmpeg，通过 image2pipe 输入按序喂入 PNG，减少“全部准备完成后才编码”的等待和逐帧图片写盘。FFmpeg 支持管道输入；具体命令和封装行为以真实文件回归为准。[FFmpeg 管道文档](https://ffmpeg.org/ffmpeg-protocols.html#pipe)

编码时钟仍由帧序号和任务帧率决定，不能使用浏览器播放时间戳。管道写入需要等待可写事件；后端缓存满时降低客户端提交速度，不能无限积压或丢帧。全部输入完成后关闭输入，等待编码及封装正常结束，核对帧数后再提供下载。

输出文件继续保存在已试写的 `.drawai-cache/`；管道化不等于把整个视频放进内存。取消、进程崩溃、网络中断和客户端离开分别定义清理与恢复策略。保留旧的离线图片序列路径作为诊断回退，禁止回退到会跳帧的实时录制。

### 5.3 复用已经完成的栅格帧

绘制阶段已有的原视频帧不能直接用于导出，因为它们不是绘制后的 SVG 画面。导出缓存必须以最终 SVG 内容、输出尺寸、白底/颜色、渲染器版本为键。同一设置重复导出或切换容器格式时，才复用匹配的栅格结果，并设空间上限和淘汰规则。

## 6. 绘制与导出的资源协调

共享一个资源预算，分别控制绘制 Worker、FFmpeg 线程、解码帧和导出帧缓冲。不能让每个排队任务都按 CPU 核数创建线程。

默认优先保证正在进行的绘制和界面响应；导出允许重叠，但其编码线程与缓冲也计入全局预算。低内存时优先减少并发和缓存，不减少输出帧或偷偷降低分辨率。

后续再增加快速编码预设、可选显卡编码和高级并发配置。显卡编码需要实际试编码成功后才能启用，不能仅凭 FFmpeg 列出了编码器就认定可用；这些不作为首轮高优先级工作的前置条件。

## 7. 交付顺序与验收

| 阶段 | 交付 | 必须满足的验收 |
|---|---|---|
| P0 | 分阶段计时、固定素材、协议及任务身份约定 | 能区分渲染、传输、计算、排队和编码耗时；记录现有结果与内存基线 |
| P1-A | 图片/视频任务队列、宿主执行器、列表与控制操作 | 多任务按序执行；切换界面不丢失；取消只影响目标任务；失败后继续下一项；结果只应用一次 |
| P1-B | 视频顺序解码、原始像素 Worker 入口、共享资源预算 | 无漏帧、重复帧和错序；采样、色彩、画风回归通过；在途内存有界；有可比较的绘制耗时报告 |
| P1-C | 导出预取、二进制上传和下载 | 人为延迟、乱序、重复提交及大帧都正确；同参数文件完整；记录传输与准备阶段收益 |
| P2 | FFmpeg 管道流水线、暂停检查点与恢复 | 准备和编码能重叠；慢帧不丢；30/29.97fps 时间戳正确；音频偏移与时长正确；中断恢复不重复提交 |
| P3 | 缓存复用、快速预设和可选显卡 | 独立测量收益、体积和画质，显卡失败可清晰回退到离线 CPU 编码 |

P1-A 与 P1-B 共用队列执行器设计，按可独立验证的小改动交付，不一次替换所有旧逻辑。导出优化在公共协议和身份规则确定后可单独推进。

首轮性能目标是让固定测试集中主要等待阶段出现稳定、可重复的改善；具体提升比例在 P0 测得基线后确定。任何优化出现帧完整性、音画同步、绘制风格或跨画布写入回归，即使更快也不作为默认路径发布。

建议新增 `src/task-queue.js`、`src/video-decode.js`、`src/task-store.js` 和对应测试；重点修改现有 `src/video-trace-pool.js`、`src/video-trace-worker.js`、`src/canvas-sessions.js`、`src/video-export.js`、`src/client.js` 与 `src/index.js`。新入口保持 Node 20 及以上兼容，不直接采用更高版本专属 API。
