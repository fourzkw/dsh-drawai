# P0：性能采集与基准测试

P0 提供分阶段采集、固定素材、冷/热启动基准和回归检查。绘制参数、输出画面、帧率与帧数保持原有行为；P1 的第一批交付见 [计算优化与应用内队列](performance-optimizations.md)。

## 在真实应用中采集

在启动 DSH 的 PowerShell 中设置变量，然后启动或重启宿主：

```powershell
$env:DRAWAI_PERF = '1'
dsh web
```

使用平时的图片绘制、视频绘制或 MP4/WebM 导出入口。完成、失败、取消或服务释放后，汇总文件保存在画布目录的 `.drawai-cache/performance/`；图片绘制记录保存在当前会话工作区的同名目录。目录已被 Git 忽略，每个日志目录保留最近 100 份报告。关闭采集时移除环境变量并重启宿主：

```powershell
Remove-Item Env:DRAWAI_PERF
```

采集默认关闭。日志只保存数字汇总、参数和运行环境，不保存原图、SVG、认证令牌或视频内容。日志写入失败不影响绘制和导出。成功的浏览器报告通过原有已验证会话、画布路径和任务令牌的入口合并；客户端不能指定日志目的地。

## 可观察的阶段

| 范围 | 记录内容 |
|---|---|
| 浏览器视频绘制 | 源数据读取请求、Base64 解码、媒体加载、seek/解码、缩放、PNG 编码、Base64 编码、各请求往返 |
| 宿主视频绘制 | 源文件快照、分块解码及写入、帧读取、Worker 排队、Worker 往返、按序提交等待、SVG 写入 |
| Worker / 图片内核 | PNG 解码、像素预处理、调色板量化、标签处理、轮廓生成、SVG 简化与序列化、指标生成 |
| 浏览器导出 | SVG 请求与图像解码、白底画布渲染、PNG 编码、Base64 编码、上传请求、编码轮询等待、下载 |
| 宿主导出 | 源文件快照、编码器试写、分块解码及写盘、PNG 校验提交、FFmpeg 编码、输出读取及 Base64 编码 |
| 数据与复用 | 帧数、PNG/SVG/下载字节数、精确重复帧复用数、调色板复用/刷新/拒绝数、在途帧峰值、导出输入及总临时文件字节数 |
| 资源 | 宿主 RSS/堆内存采样峰值、进程 CPU 时间、宿主事件循环延迟、浏览器 Long Tasks（支持时） |

每阶段只保留 `count / totalMs / maxMs`，不会因视频变长而无限追加采样数组。`wallMs` 表示宿主任务从创建到结束的时长。浏览器前缀为 `browser.`，Worker 前缀为 `worker.`。

注意读数的边界：

- 并行 Worker 的累计耗时、Worker 往返和请求往返相互包含，**不能把所有阶段相加当作总时间**。绘制请求往返包含排队、计算和响应处理，不等于纯网络传输时间。`orderedCommitWait` 与精确帧的 `reuseWait` 分开记录。`exactFrameHash` 记录 PNG 内容摘要耗时，`worker.paletteValidation` 记录前景适配检查，该检查也包含在量化阶段的总时间中。早期日志的 `scaleAndFingerprint` 已由 `scaleFrame` 替代。
- 图片完整分析包含参考档位和其它档位，内核阶段会累计所有尝试；视频仍只计算选中档位。`svgSerialization` 包括原有预算阶梯中的简化、拼接及重试，不能解释为单纯字符串操作。
- RSS 每 250ms 采样，覆盖宿主进程和 Workers 的共同驻留内存；它是采样值，不保证捕获瞬时尖峰。堆内存只描述采样所在主线程。同步图片计算会阻塞定时器，不能将其采样值当作精确分配峰值。
- FFmpeg 子进程和浏览器进程的 RSS 暂不可用，报告明确为 `null`。进程 CPU 时间、事件循环延迟和 Long Tasks 也可能包括同一进程/窗口中的其它任务，不能当作单任务独占值。
- Long Tasks 从宿主返回采集开关后观察到浏览器任务结束，浏览器不支持时省略；异常路径始终断开观察器。宿主已失败的任务可能在浏览器回传前结束，此时以宿主错误阶段日志为准。
- 导出日志包含试写及下载，FFmpeg 编码耗时单列。直接导出原生 MP4 的快捷路径没有重新编码，因此不会产生离线编码报告。

## 固定测试集与自动基准

```powershell
# 小尺寸冒烟测试，默认包含五类画面和两个现有图片夹具
npm run bench:performance -- --suite smoke --repeats 3

# 同时生成可导入画布的有声 MP4 / 透明 WebM
npm run bench:performance -- --suite smoke --repeats 3 --videos

# 480p / 1080p × 30 / 29.97fps × 五类画面，外加图片夹具
npm run bench:performance -- --suite standard --repeats 3 --videos

# 只测指定场景
npm run bench:performance -- --suite standard --case static-480p-30,motion-1080p-29.97 --repeats 3

# 只准备固定素材，后续在真实应用内测试
npm run bench:performance -- --suite standard --videos --prepare-only

# 4K 复杂画面及 60 秒长片；执行前预留时间、磁盘与内存
npm run bench:performance -- --suite stress --repeats 3

# 未安装 FFmpeg 时单测绘制，导出不会伪装成通过
npm run bench:performance -- --suite smoke --trace-only
```

五类画面是静止、缓慢运动、快速切镜、复杂彩色、透明背景。视频素材由固定算法生成 PNG，再按需编码为有声源视频；图片使用已有校准夹具。每组记录尺寸、帧率、帧数和源 PNG 序列的 SHA-256。标准视频每组 30 帧，压力组包含 4K 30 帧及 480p 1800 帧。素材生成在测量区间之外。

结果写入项目的 `.drawai-cache/benchmarks/<时间>/`：

- `environment.json`：Node、FFmpeg 版本、CPU、系统内存、源码摘要及测试套件。
- `fixtures/<场景>/`：固定 PNG、素材清单及可选源视频。
- 各次运行的 `.drawai-cache/performance/*.json`：完整阶段数据。
- `summary.json`：按素材、任务类型、冷/热分组，给出至少 3 次的中位数、最小/最大值、处理速度、阶段中位累计耗时和宿主采样内存峰值。

冷启动每次使用新 Node 进程；热启动在同一进程内先执行一次预热并排除该次，再测指定次数。视频复用同一个 Worker 池。每次导出仍会创建新的 FFmpeg 进程，因此这里的“热”不代表常驻编码器。冷/热都不清空操作系统磁盘缓存。图片的热启动指同进程重复计算。

自动视频基准目前是**宿主局部基准**：PNG 输入 Worker，不模拟浏览器 seek、帧/调色板复用和网络；导出直接提交固定 PNG，不包含 SVG 栅格化，也不代表绘制后画面的编码复杂度。它用于隔离计算、排队、落盘和编码，不能用其帧速率替代画布的实际绘制速度。图片基准使用实际 `includeDrawing` 完整分析路径。

测试时关闭其它计算任务，保证同一机器、电源模式、参数及源码版本；不要并行启动多个基准。4K/长片默认不执行。生成的基准素材保留以便复测，使用后可自行清理对应时间目录。

## 浏览器端到端对照步骤

1. 先生成标准源视频，在真实应用中开启采集，导入固定素材。
2. 固定碎片档位、画风、颜色、去背景、采样起点、尺寸、时长、帧率和导出格式。冷启动时重启宿主及页面；热启动在同一宿主/页面预热一次，再连续运行至少 3 次。
3. 保留相同素材对应的绘制和导出报告，按任务参数比较 `wallMs`、`browser.*`、Worker 阶段和输出帧数。对长片同时观察 RSS、临时文件量及界面响应。
4. 用现有视频回归检查验证 30/29.97fps 的帧内容、时间戳和音频；优化前后的真实素材还需视觉核对采样和画风。性能日志不替代正确性检查。

当前已执行宿主局部基准与自动回归；真实应用的完整标准矩阵、4K/长片压力测试及浏览器进程峰值采样尚未完成。它们不能标记为已测通过。

## 首轮宿主基线（2026-10-17）

环境为 Windows x64、Ryzen 9 8945HX、32 个逻辑 CPU、约 32GiB 内存、Node 22.19.0、FFmpeg 7.1；Worker 池上限 4。下表为独立复测的中位数，各组冷/热各取 3 次，热启动额外预热一次。绘制参数为 medium / default / 6 色 / 保留背景，视频各 30 帧。

| 素材 | Worker 局部绘制冷/热 | PNG 序列导出冷/热 |
|---|---|---|
| 静止 854×480，30fps | 4.279s / 4.682s | 0.578s / 0.608s |
| 缓慢运动 1920×1080，29.97fps | 23.723s / 23.990s | 1.055s / 1.064s |

这组测试不启用帧和调色板复用，也不包含浏览器 seek、传输和 SVG 渲染；静止素材在真实应用中可复用，不能把上表解读为真实画布的耗时。热启动也不保证更快，后续比较必须继续记录波动。

1080p 热启动样本中，Worker 累计量化约 40.18s、标签处理约 41.28s，而 PNG 解码约 0.99s；这些是多 Worker 累计值，实际总墙钟约 23.99s。采样宿主 RSS 最高约 819MiB。可据此判断：在这组无复用的局部样本中，量化与标签处理占主要计算成本，不能仅靠增加线程或减少 PNG 解码来承诺大幅提速。P1 应同时核对真实复用命中率及浏览器耗时，再决定计算内核和传输优化的先后。

原始阶段数据及素材清单位于本机 `.drawai-cache/benchmarks/2026-10-17T12-18-24-297Z/`。小尺寸五类素材和现有两张图片夹具也已运行；完整标准矩阵及压力组保留为后续扩展验证。

## 报告协议和后续任务身份

报告协议版本为 `schemaVersion: 1`，包含随机 `id`、`kind`、`status`、`startedAt`、`environment`、`metadata`、`wallMs`、`stages`、`counters`、`peaks`、`resources`。客户端汇总只允许有界名称与有限非负数字，不信任客户端提供的路径或任意对象。`performanceId` 是关联诊断的编号，不提供任务访问权限。

当前继续使用既有 `sessionId + drawioAbs + clip + token` 鉴权。P1 的用户任务 ID 将独立于执行令牌，并绑定工作区、会话、画布、页面、源节点/内容摘要和冻结参数；重试产生新的执行编号，保留同一逻辑任务关联。采集 ID 不代替队列状态、幂等键或持久化检查点。

P0 的测试入口为 `node tools/check-performance.mjs`，已接入 `npm test`；检查汇总有界、异常清理、日志隔离、Worker 等待和计时开关前后 SVG 完全一致。
